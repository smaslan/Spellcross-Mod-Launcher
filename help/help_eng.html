Spellcross MOD Launcher

   Spellcross Mod Launcher is simple tool for runtime building of game data archive mods and launching Spellcross game. This tool can build modded game data archives from original game files and added or modified user files based on simple definition file. It can then replace game archives, launch the game and restore original game files afterwards. It can be of course also used to launch original game without mods. It also contains simple SAVE games manager for making backups.

Disclaimer and precautions

   The tool is provided without any warranty! It modifies, moves and removes files, so be cautious what you do and I strongly recommend to make backup of your game files and save games before you run this tool. Any potentially risky operation will be prompted.

1 - Basic setup

   First thing after first startup is to define few paths in the main panel. First, specify Spellcross installation folder, e.g. "C:/games/SPELCROS". If your game version involves CD (some versions may run without), specify also path to Spellcross CD path. Here it is important to note that if the game mod should modify also CD files (e.g. videos and unit renders), you must copy content of CD to some local folder, e.g. to "C:/games/SPELLCD" because mounted CD ISO is read only. If you have several Spellcross patch version EXE files in your Spellcross installation folder, so you may select desired Spellcross executable to launch (should be listed, default is "SPELCROS.EXE"). Next, specify Virtual CD drive letter to which Spellcross CD will be mounted (applies to both DOSbox mod and native Win32 modes). Next, define your DOSbox path (for DOSbox mode only). You can optionally disable "autoexec.bat" and start fullscreen in DOSbox. Next, select Spellcross Run mode. This tool was originally made in the era of 32bit WinXP which could still run 16bit DOS apps natively using its integrated NTDVM and DOSbox was a bit too slow back than. So, there is still legacy option "Win32" to run it natively e.g. in virtual machine. But now the only viable option is "DOSbox" mode. Finally, if you want to run mod, select Mod path. For each mod you can specify if it's allowed to modify CD game files (default: yes). Last option is to move SAVE games folder with the mod. The idea here is that your save games will be copied to selected mod folder when you finish playing. On the next startup they will be moved to the game location (originals are preserved/backuped) and will be moved to mod folder again when you finish playing. This way you can have multiple sets of save games not colliding with each other. And that is it for basic setup.


2 - Installing mods

   Mod installation is trivial. Just download mod and unpack it to some folder and set the Mod path. Here it is important to note the mod should be placed to the same drive letter as the game, so if you have game e.g. in "C:/games/SPELCROS", place it anywhere to "C:/". This will ensure the replacement of game data files is fast and no data are copied (system will only change file locations in file system allocation tables). Whereas when you have mod at different drive, it will have to copy all its data there and back again which might be up to some 500 MB of unnecessary SSD drive writes per run. Note the tool is also optimized, so it will not generate modded archive if it detects its content is identical to the original. It will also not rewrite any files if they do not change. Some mods can be found here: https://spellcross.kvalitne.cz/mod/spell_mod_builder.html.

3 - Running game and mods

   After setting up paths, you can run the original unmodified game by button Run Original or run modded version using Run Mod. For runnig mod it is not necessary to do anything else. The tool will automatically build and swap the game archives and restore them after the game is finished. There is no need to use any other functions.

4 - Advanced usage

   There are few other actions useful for mainly for development of mods. First, in the Setup menu you can edit various config files and run Spellcross "SETUP.BAT". In the menu Mod you can choose Build mod. This will make modded archives into the mod's MAKE folder. Option Force rebuild mod will make mod files and force write operation even when content is not changed. Option Build and swap will build mod files and replace the original game files and they will stay there until restored. Option Restore original will move the modded archives back to the mod's MAKE folder and restore original game files from their backup location. Note all these operations are done automatically when you run the mod by button Run Mod. The restore operation is called automatically before any other action to ensure game is always in its original state. In some rare cases the restore operation might fail. This can happen in very unlikely case when PC crashes during game archives swap operation. But it can also happen when you are viewing content of some folder or file that is to be moved by some of the tool operations. The restore can be retried any number of times. The tool stores state of modded files (and saves) in file "mod_state.ini", so it should be able to recover automatically even after crash or restart. If that for some reason fails consistently, you can use option Cleanup mod config which will clear the state file. But this will almost certainly lead to inconsistent state of game files (and possibly save games if you use option Move SAVE games), so that is really the last resort option. After this operation you'll likely have to manually restore everything from your backup.
   In menu Run you can use Build launch files which will generate various game startup BATch files to the game installation folder. You can run those outside this tool if you wish. Note these are generated automatically whenever you start the game via this tool.

5 - Save game management

   As mentioned above, the tool has option Move SAVE games. This will move your saves made during modded game play to the mod sub-folder "save". When you run the modded game again it will move them to game "SAVE" folder. This will ensure you can have separate sets of save games not mixing together because modded saves are usually not compatible with original game ones (causes game crashes). This is why there are two sets of operations for any save game action in this tool. One set works with original game save in its folder "SAVE", the other set works with saves copy in the mod folder.
   Another save feature is fast backup and restore of "SAVE/WORKDIR". There are game missions which are terminated without option to reload when some critical unit dies (typically convoys). This is very annoying feature. But there is easy workaround. When you leave war map with save state option, the game stores state to game "SAVE/WORKDIR" folder. When you exist the game, you can backup this folder by button Backup WORKDIR. Then you can continue gameplay again. When mission fails, you can again exit the game and use Restore WORKDIR to reset the save game state and when you run the game again you continue when you ended before. This is basically an extra save game. It's kind of cheating, but might be handy.

   In menu Savegame you can run Manage SAVEs. This will run simple tool for making backups of the whole set of save games. It basically makes named copies of the game "SAVE" folder (or from save copy in mod folder). Then you can restore from these either all saves at once or you can pick one particular. The manager will always prompt user with details of operation so it should be safe.

6 - Making mods

   This section will briefly describe how the mod structure works. An example of a typical structure of mod folder is following: 

./data/common/M01_01A.DEF
./data/common/RESEARCH.DEF
./data/common/...
./data/units/MAMUT/000
./data/units/MAMUT/001
./data/units/MAMUT/...
./info/info.html
./info/...
./make/common.fs
./make/units.fsu
./config.def

   The whole concept of modifications is based on maximum usage of original game data. It would not be practical to distribute all game files and it would be also questionable due to the copyright reasons. Therefore, modded game files are generated on runtime when the mod is launched from original game files as a basis and the mod contains only new or modified files to be implemented. Mod structure is defined in its "*.def" file which is C++ style-ish format. This file consists of few sections. Fist section is "class PATH" where we define necessary path variables for further operations. Example of such section: 

class PATH
{
    // --- REQUIRED ITEMS (reserved names) ---
    // make folder, relative path to folder to store output archives
    MAKE=make;

    // --- OPTIONAL ITEMS ---        
    // links to original game data files
    COMMON=%SPELL%\DATA\COMMON.FS;
    UNITS=%SPELL%\DATA\UNITS.FSU;
    
    // folder with this mod data
    DMOD=data;

    // the mod data folders
    MOD_COMMON=%DMOD%\COMMON;
    MOD_UNITS=%DMOD%\UNITS;
}

The "MAKE" variable is mandatory and defines where the tool generates modified archives. In this case it is to the mod sub-folder "make". All other variable definitions are optional up to user needs. Any variable definition can contain reference(s) to previously defined variable in format %variable_name% that will be expanded during execution. The tool recognizes three predefined variables: %SPELL%, %SPELLCD% and %SPELLANY%. %SPELL% and %SPELLCD% are expanded to paths Spellcross installation folder and Spellcross CD path as set in the main tool panel. %SPELLANY% will automatically choose either of %SPELL% or %SPELLCD%, which is handy because different Spellcross versions can have the data files located differently between CD and installation folders. Note that the path definitions can be also placed to a separate "class SRC". This is deprecated method, but still supported because of old version of this tool.
   In the example above we define few more variables. Variables "COMMON" and "UNITS" point to the original game data archives. Variable "DMOD" points to sub-folder "data" in the mod folder. Finally, we define two more variables "MOD_COMMON" and "MOD_UNITS" pointing to the particular mod data folders.
   Finally, follow sections that define content of particular game archives to be built. Example for "COMMON.FS" archive is following: 

class COMMON.FS
{
    replace=1;                      // by default overwrite previous data by each add() command
    optional=0;                     // optional flag (default 0: generate error if source not found)
    add(%COMMON%);                  // add all data from original game archive COMMON.FS
    add(%MOD_COMMON%,M01_01A.DEF);  // add specific file from mod "data/COMMON" folder
    add(%MOD_COMMON%,*.CUR);        // add wildcard key matching files from mod "data/COMMON" folder
    add(%MOD_COMMON%);              // add all files from mod "data/COMMON" folder
}

   The switch "replace=1" means every following "add()" command will replace already added files. "replace=0" means it will only add new ones. This can be also specified individually in the "add()" command itself: 

add(source);                // add all files from "source"
add(mode,source);           // same as above, "mode" defines addition method NEW (add only new files) or ALL (overwrite existing)
add(source,wildcard);       // add files matching "wildcard" key (e.g. *.LZ or LEVEL_??.DEF)
add(mode,source,wildcard);  // same as above with "mode" switch

Switch "optional=1" can mark archive as optional, so tool will not generate error if "source" data in "add()" command is not found. Default is "optional=0", which means the "source" must exist.
   All other archives are the same with exception of "UNITS.FSU". This game archive contains unit sprite graphics and it is internally structured per-unit. Each unit has name up to 5 characters long and it contain sprites with names of exactly 3 characters with no extensions. These files are LZ compressed. When adding data to this archive from a folder (in the example above from a folder "data/units"), the folder must contain sub-folder with the name of the unit, in the example "MAMUT". Example is following: 

class UNITS.FSU
{
    add(%UNITS%);              // add all data from original game archive COMMON.FSU
    add(%MOD_UNITS%,MAMUT);    // add unit "MAMUT" data from "data/UNITS" folder    
}

   Each mod can have its description in HTML format. The description is placed in sub-folder "info" of the mod and is named "info.html". This file can be displayed by the tool.
   For maximum simplicity I provide template of mod in folder of this tool (sub-folder "mod_template"). It is a skeleton with *.def file prepared so it will load all original game data and then adds and eventually overwrites it with mod content from the mod data folders. So all that needs to be done is to place new or modded files to the mod data folders.
